R1 -- LocalVar%AWC_complexangle IS NEITHER COMPARED NOR SUPPLIED NON-ZERO.  5
     Category (c): an instrument gap, in TWO places, both nameable.

   151  1dab0371  const_tweak    'for (int i = 0;' -> 'i = 1'   the zeroing loop
   153  7acaa843  const_tweak    '.im = 0.0' -> '1.0'
   174  221fb7c7  arith_op       'K - 1' -> 'K + 1'             on .im
   174  30539381  const_tweak    '1' -> '2'                     on .im
   163  97b678b5  arith_op       'LocalVar->Azimuth + phi1' -> '- phi1'

MEASURED, on the corpus this score was computed over: the generated test source
contains ZERO `VITCMP("LocalVar.AWC_complexangle` lines -- the COMPLEX(DbKi)
view field is absent from R4's out-parameter list entirely -- and the field is
supplied as (0.0, 0.0) in every case. So the zeroing loop has nothing to zero
and the imaginary half of the accumulator is an output no case can read.

97b678b5 IS RECLASSIFIED HERE, and the first census's G10 account of it is
retracted. `phi1` is `PARAMETER :: phi1 = 0.0`, so `Azimuth + phi1` and
`Azimuth - phi1` can differ only in the SIGN OF ZERO. A signed zero entering
`amp*EXP(complexI*angle)` reaches `cos` -- which is even, and returns the same
bits either way -- and `sin`, which is odd. The real half of the accumulator is
therefore identical on every input, and the real half is the only half that
reaches `LocalVar%PitCom`. The difference exists and lives entirely in `.im`.
So this is not a corpus weakness about negative zero; it is the same
uncompared field as the other four.

THE INPUT THAT KILLS ALL FIVE: a case supplying a non-zero AWC_complexangle,
compared by a generator that enumerates a COMPLEX field of a view struct as two
outputs. Neither exists. **This is a GENERATOR change, in R4's out-parameter
enumeration and in the case emitter, and it is escalated in DECISIONS.md.**

MEASURED: ZERO cases of 21236 have AWC_harmonic(1) == 0, and zero hits in all 27
gate scenarios. Unchanged from the first dispatch, and the corpus repair could
not touch it: `AWC_harmonic` is an ALLOCATABLE INTEGER array, `generate._fill_array`

THE ARM IS NOT DEAD, and the negate_cond run is what says so: negating either
guard moves 6309 and 6972 of 21236 cases. What no INPUT reaches is the guard

THE CAUSE IS NAMEABLE TO A LINE. `predicate_knobs_from`
(scripts/vit_harness.py) matches `NAME <op> LITERAL` where `_NAME` is
`[A-Za-z_]\w*(?:%[A-Za-z_]\w*)*` -- no subscript group. So
`CntrPar%AWC_harmonic(1) == 0` produces no knob at all. Its two siblings in the
same file, `relational_pairs_from` and `divisibility_pairs_from`, BOTH carry
`(?:\(\s*(\d+)\s*\))?` for exactly this shape, and `predicate_knobs_from`
already returns `(param, index, values)` and already handles a non-None index
through `_knob_overrides`. The machinery is there; the pattern does not reach it.

THE INPUT THAT KILLS ALL FIVE: AWC_Mode 3 or 4 with AWC_harmonic(1) == 0.
Escalated in DECISIONS.md.

R4 -- resP IS HELD AT ALL ZEROS, WHICH COLLAPSES ResController.  2
     Category (b), blocked by a stated instrument limitation.

   254  b796d413  index_offset    'AWC_CntrGains[1]' -> '[2]'      ki's index
   255  f337e5a2  swap_operands   'AWC_freq[Imode - 1]' -> '[1 - Imode]'

MEASURED, and reported by the harness about itself:

    UNOBSERVABLE LocalVar.resP: nested type, zero-initialised (not varied)
                                and compared bytewise after the call

`ResController`'s body is

    b0 = 4 + omega**2*DT**2      omega = 2*PI*freq
    a0 = b0*kp + 2*DT*ki
    ResController = 1/b0*( -b1*OutLast1 - b2*OutLast2
                           + a0*error + a1*InLast1 + a2*InLast2 )

and `OutLast1`, `OutLast2`, `InLast1`, `InLast2` are the four `resP` arrays --
zero in every case. Four of the five terms vanish, and what is left is

    ResController = kp*error + 2*DT*ki*error / (4 + (2*PI*freq*DT)**2)

`b1`, `b2`, `a1` and `a2` are computed and multiplied by zero. `freq` enters the
answer ONLY through `b0`, and `b0` only divides the `ki` term -- so BOTH mutants
move the same single term, and at the magnitudes this corpus draws
(`freq` and `DT` on their +/-1e3 ramps) `(2*PI*freq*DT)**2` is of order 1e13 and
annihilates it against `kp*error`.

That is why the three sibling index mutants on the PIController call at :260 and
on `kp` at :254 are all KILLED and these two are not: `PIController` adds
`DT*ki*error` with no denominator, so its `ki` reaches the output directly.

f337e5a2 carries a second fact worth stating: at `Imode == 2`, `[1 - Imode]` is
`AWC_freq[-1]`, one element BEFORE the array. It is an out-of-bounds read as well
as an annihilated one.

THE INPUT THAT KILLS THEM: a case supplying non-zero `resP` history, with `freq`
and `DT` small enough that `b0` is of order 1. The first half is a generator
capability that does not exist -- a nested derived type inside a view struct is
zero-filled, never varied -- and it is what the harness's own UNOBSERVABLE line
has been reporting all along. Escalated in DECISIONS.md.

R5 -- A BOUNDARY BETWEEN A PARAMETER AND AN EXPRESSION OVER ONE.  1
     Category (c): a crossing rule this generator does not have.

   312  2d7ffe20  compare_op     '>' -> '>='

`LocalVar%Time .GT. 1/CntrPar%AWC_freq(1)` and `.GE.` differ on exactly one
input: `Time` equal to `1/AWC_freq(1)` to the bit. MEASURED: no case of 21236
is on it, and none can be by accident.

THIS IS THE ONE SURVIVOR THE DRIVER NAMED THAT IS STILL HERE, and the reason is
structural rather than a matter of range. The generator has a rule for exactly
this shape -- `relational_pairs_from`, which sets one side of a predicate to the
OTHER SIDE's value in the same case -- and it requires BOTH sides to be
parameters. Here the right side is `1/AWC_freq(1)`: an EXPRESSION over an
element of an allocatable array. `reduction_pairs_from` is the same rule
extended to `MINVAL`/`MAXVAL` of an array, added for `interp1d`'s endpoint
branches, whose survivors were this same `<` against `<=` pair. This is that
extension one step further out: a crossing against a RECIPROCAL.

THE INPUT THAT KILLS IT: `Time == 1/AWC_freq(1)` exactly, in Mode 5.
Escalated in DECISIONS.md.

   193  e9d4580d  index_offset   'AWC_TiltYaw[1] = 0.0' -> 'AWC_TiltYaw[2] = 0.0'

`AWC_TiltYaw` is `static double AWC_TiltYaw[2]`, so the mutant stores one element
PAST it. That is undefined behaviour, not a different implementation, and this is
the shape unit #4 recorded for `GetRoot`: *"each surviving mutant there was a
memory error no value comparison can see."*

THE FIRST CENSUS WAS WRONG ABOUT THIS ONE and the correction is the point. Its
G8 grouped e9d4580d with df13f212 as "moving either reset to another element
changes nothing", which is right about the observable values and wrong about the
program. df13f212 moves the store to a VALID element that the loop below
overwrites, and IS declared equivalent, with its reasoning in
mutation/ActiveWakeControl.equivalences.md. e9d4580d is not, and must not be:
declaring an out-of-bounds write equivalent would be using the score to bless
undefined behaviour.

THE INSTRUMENT THAT KILLS IT: `-fsanitize=address` on the harness build.
Escalated in DECISIONS.md.
