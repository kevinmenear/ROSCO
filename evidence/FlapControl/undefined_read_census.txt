TWELVE OF TWELVE ARE THE SAME CONFIGURATION AND IT IS THE PREDICTED ONE:

    Flp_Mode == 2  AND  iStatus == 0  AND  restart == 0  AND  NumBl >= 1

which is exactly the region in which `Controllers.f90:670` passes
`RootMyb_VelErr(K)` -- a local the reference DECLARES AND NEVER ASSIGNS -- into
`PIIController` on the branch that reads it. `NumBl == 0` is absent because the
loop runs zero times there; `NumBl == 3` is absent because 3 is not one of R6's
knob values for it ([0, 1, 2]).

WHY ONLY `LocalVar.piP` MOVED, AND WHY THAT IS LUCK RATHER THAN A PROPERTY.
`PIIController` computes

    PTerm  = kp*error
    ITerm  = saturate(ITerm  + DT*ki *error , min, max)
    ITerm2 = saturate(ITerm2 + DT*ki2*error2, min, max)
    result = saturate(PTerm + ITerm + ITerm2, min, max)

All twelve cases hold `Flp_Kp = 0` -- R6's isolating 0.0 pin, not the base draw
-- so `PTerm` is 0 whatever the undefined `error` is, and with `Flp_Ki = -300`,
`DT = 300` and `error2 = 0 - 600` the sum saturates to the same limit on both
chains. The difference survives only in `ITerm`, which is `piP`'s business and
is compared bytewise. At ANY non-zero `Flp_Kp` the undefined value reaches the
result directly and `LocalVar.Flp_Angle` and `avrSWAP` diverge as well.

That is why `no_oracle = "LocalVar_piP"` was considered and NOT taken. It would
have been green on this corpus, silent about the cause, and wrong the moment the
corpus moved -- and it would have cost the piP comparison on the 9709 cases
where the reference does have an answer for it.

WHAT WAS DONE INSTEAD is `harness/ranges.toml`'s new `implied_by` entry, which
states the relation `restart == (iStatus == 0)` that `ReadAvrSWAP` establishes
before every controller call. See that entry for the citation and the cost.
