## THE 104 ARE NEW, AND THEY ARE THE BASE-DRAW CHANGE SHOWING UP AS A NUMBER

`alloc = 0, other` has 7,523 cases of which **104 changed aviFAIL**. In the
third dispatch's table that cell was 3,036 cases and **0** changed it. The cell
is "the reference set a status but its returned ErrMsg matches no arm the
classifier knows", and the reason there are now 104 of them is R13:

    harness/ranges.toml   has_AllowDefault = { values = [1, 0] }
                          AllowDefault     = { values = [0, 1] }

R13's 256-case staging-capacity block is taken with every other input at its
BASE DRAW, and until this dispatch that draw put `has_AllowDefault = 0` -- the
default ALLOWED -- so the block sat on the one arm that assigns no message at
all and swept a capacity against a zero-length string. Reordering the two flags
(neither value is removed; nothing is narrowed) puts the block on the
`.NOT. AllowDefault_` arm, whose message is 112 bytes. The run's own stderr is
the record of it:

    VIT: ParseDbAry_Opt: ErrVar%ErrMsg needs 112 bytes, the staging buffer
         holds 109/110/111; the assignment is refused
    VIT bridge: ErrVar%ErrMsg assignment of 112 bytes exceeds the ...-byte
         buffer the caller supplied; left unchanged

Both sides refuse the same assignment -- the translation at `assign_errmsg` and
the generated Fortran bridge at the same length -- so the case still PASSES, and
the reference comes back with `aviFAIL = -1` and the ErrMsg it was handed. That
is the cell.

**IT IS THE WHOLE REASON SURVIVOR `b5366e74` DIED.** `s.size() > cap` and
`s.size() >= cap` differ on exactly one input: the capacity that equals the
message length. Across 16,512 cases there was no such input; across 17,520 there
are 104 cases in the block and one of them sits at cap = 112.
