  `match_word`'s FIRST INDEX (1): 42edf275, `k = 0` -> `k = 1`, which skips
  comparing the word's first character.

    ARGUED EQUIVALENT AND DELIBERATELY NOT DECLARED. The mutant matches a strict
    superset: records whose characters 1.. spell `an` / `nf` / `nfinity` but
    whose character 0 does not spell `n` / `i`. On every such record the branch
    collects `buf` beginning with that character and calls
    `strtod("±" + buf)`, which cannot consume a field containing `a` or `n` at
    position 1, so it returns BadNoStore. The ORIGINAL, having not matched,
    scans the same field as a number and either fails the same way or parses a
    prefix and stops at a non-separator, which the caller turns into the same
    5010 with nothing stored. Same IOSTAT, same untouched element.

    NOT DECLARED because that is an argument and not a sweep: it rests on "no
    complete numeric field contains `a` or `n`", which is true of strtod and is
    the sort of claim a payload spelling (`nan(...)`) exists to break. It sits
    beside the two splits the third dispatch made for the same reason --
    lower()'s 'A' bound was not declared while its 'Z' bound was.

  THE IEEE PAYLOAD BUFFER (3) IS A REGION THAT DID NOT EXECUTE UNTIL THIS
  DISPATCH, and its three survivors are the boundary of a buffer, not of a
  record.

    1df32d1d  L234  `n < 62` -> `n <= 62`   the payload LENGTH bound
    5b1c8101  L234  `62` -> `63`            the same bound from the other side
    1beac345  L237  `buf[n]` -> `buf[n + 1]`

    THE RECORD THAT KILLS THE FIRST TWO: an IEEE word with a 62-character
    payload -- `nan(` + 58 characters + `)`. The corpus spells `inf`, `Infinity`
    and `nAn`, which are 3, 8 and 3 characters, so `n` never approaches 62.

    1beac345 IS AN INSTRUMENT GAP AND NOT A CORPUS GAP, and it is a new one.
    Writing the NUL one byte late leaves `buf[n]` holding whatever the
    uninitialised `char buf[64]` held, and both indices are INSIDE the array --
    so AddressSanitizer is silent by construction. Catching it needs
    MemorySanitizer, which reports an uninitialised READ; `--sanitize` builds
    with address,undefined. Naming it as MSan rather than as "a wider corpus" is
    the point: no record kills this one.

  THE EXPONENT (4). Three of the four need a record that ends INSIDE AN
  EXPONENT, which is the one boundary shape `_RECORD_TAILS` does not build.

    a0007207  L276  `p < len` -> `p <= len`     needs a record ending `…1E`
    e2d47adf  L276  `rec[p]` -> `rec[p + 1]`    needs `…1E` and a sign at 2048
    91f2ce24  L276  `rec[p]` -> `rec[p + 1]`    likewise, the `-` half
    7d8e5de9  L279  `int edigits = 0` -> `1`    needs `.e` before a separator

    THE FOURTH IS THE INTERESTING ONE AND IT IS CHEAP. With `edigits` starting
    at 1 the malformed-exponent rejection never fires, and on almost every
    record that changes nothing -- the reconstructed text still ends in a letter
    or a sign and `strtod` still refuses it. It changes the ANSWER on exactly one
    shape: a field with a decimal point, NO mantissa digits and a malformed
    exponent (`.e` then a separator). There the original returns BadNoStore and
    stores nothing, while the mutant falls through to `if (digits == 0)` and
    returns BadStoreZero, which STORES 0.0 into the element. The reference's own
    behaviour on that shape is measured -- `-.e ` is iostat 5010 and NOT stored,
    `.e1 1.0` is 5010 and STORED 0.0 (fortran_io_probe2.txt) -- so a corpus with
    a `.e` lead has an oracle for it.
