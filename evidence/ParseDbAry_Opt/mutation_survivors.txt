AND WHY, PER REGION. None of these is a claim that the translation is wrong; all
of them are claims about what this campaign's instruments can see.

  THE PRINT RECORD (9) IS COMPARED BY NOTHING, and that is unchanged from the
  first dispatch and now measured twice over. The differential harness compares
  out-parameters; the gate compares simulation channels; this record goes to
  stdout -- the same stdout the harness parses its own JSON out of. The negative
  control is a gate run: mutant ae3f319a (`16 - decexp` -> `16 + decexp`) moves
  0 of 5,252,000 values, revert-verified
  (gate/ParseDbAry_Opt.redtest.survivor-ae3f319a.json). Killing these needs a
  DIFFERENT INSTRUMENT -- one that compares the two sides' stdout -- not a bigger
  corpus. They are NOT declared equivalent: they are reached, they change the
  record, and nothing looks.

  `match_word` (7 of the 16) IS EXECUTED ON EVERY VALUE AND NEVER MATCHES. The
  corpus contains no record spelling `inf`, `infinity` or `nan` at a value
  position, so the function returns false at every call and a mutant that makes
  it return false differently is invisible. This is a CORPUS fact, which is why
  none of them is declared equivalent -- the moment a case spells `nan` they
  become killable. The block they guard IS declared unreachable: lines 232-242
  are never executed (evidence/ParseDbAry_Opt/line_coverage.txt), and the six
  mutants inside it are among the 30.

  `p < len` -> `p <= len` (5 of the 16) NEEDS A RECORD THAT ENDS INSIDE A VALUE.
  The internal-file record is `Line`'s declared width, MaxLineLength = 2048,
  blank-padded, so a scan reaches `p == len` only if the 2048th character is a
  digit or a sign. No case supplies one. The sixth instance of the shape,
  0a3516d1 at parse_real's entry, IS declared equivalent -- there the caller has
  already established `p < len` (mutation/ParseDbAry_Opt.equivalences.md D), and
  the difference between that one and these five is the reason the declarations
  are per mutant rather than per line.

  `rec[p]` -> `rec[p + 1]` (5 more) READS THE NEXT CHARACTER OF A 2048-BYTE
  BLANK-PADDED RECORD. The sanitised sweep is the instrument for this class and
  it was run: `--sanitize` killed 2 of them (4d44e6d2, f6007814) and left these,
  because the read is INSIDE the allocation and lands on the padding. So they
  are not out-of-bounds; they are reads of a character the corpus makes blank.

  THE `list_read_reals` FIVE are the `;` terminator, the repeat-count scan and
  the trailing-comma skip. `grep -cE '[0-9][*]' Examples/DISCON*.IN` over all 22
  files the 27 scenarios read returns 0, and the gate confirms it: survivor
  48542e3d in the same branch moves 0 of 5,252,000
  (gate/ParseDbAry_Opt.redtest.survivor-48542e3d.json). Reachable in principle,
  unreached by both instruments.

  `b5366e74` (assign_errmsg, `>` -> `>=`) refuses a staged assignment whose
  length exactly equals the capacity. R13 sweeps the staging capacity 0..255
  bytes above what each case supplies, so one case in each block sizes the
  buffer TO the message -- but the composed-capacity arithmetic of RUNBOOK's
  unit #48 entry applies here too and this unit has two staged assignments on
  the path. Not investigated further at this dispatch; named rather than
  declared.

  `b2bbedf3` (`std::max(NumWords, 0)` -> `NumWords`) cannot bite while
  `AryLen = { lo = 0, hi = 32 }` is stated, since `NumWords = AryLen + 1 >= 1`.
  That is a fact about the stated DOMAIN, not about the program, so it is left
  alive rather than declared -- its sibling `dd749c6b`, which merely swaps
  `std::max`'s arguments, IS an equivalence and is declared.
