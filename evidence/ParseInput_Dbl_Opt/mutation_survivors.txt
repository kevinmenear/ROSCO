None of these is declared: `--equivalences` is a claim that the two programs

  f13a04da  compare_op    L213  p < len -> p <= len

  THE REASON IS READABLE IN THE SEARCH RATHER THAN ARGUED. At `p == len` these
  five read `rec[200]`, which is not past any allocation: `Words` is
  `CHARACTER(MaxParamLength) :: Words(2)`, one contiguous 400-byte object, and
  byte 201 IS `Words(2)(1:1)` -- the first character of the parameter name
  `FindLine` just matched. The search puts `PC_KP` there, a real name from
  `Examples/DISCON.IN`. 'P' is not a digit, not a '.', not a '+' or '-' and
  not an e/d/q, so all five guards take the same branch either way.

  A Fortran parameter NAME cannot begin with a digit, so in the SHIPPED
  program these five may well be equivalent. In the harness corpus `VarName`
  is an arbitrary string and can, so they are reachable there -- which makes
  them a corpus gap and not an equivalence, and is why they are left open.

  This is also the reason `--sanitize` bought 5 kills on this unit against 41
  on `ParseInAry_Opt`: there the record is a 2048-byte `std::vector<char>` and
  the same edit reads one byte PAST it, which AddressSanitizer sees. Here it
  reads a letter.

  8e796788  const_tweak   L159  for (k = 0; ...) -> k = 1  in match_word
            Skips the comparison of the IEEE word's FIRST character, so a
            record beginning `xnf` would match `inf`. The search contains
            `xnf`, `0an` and every other length-3 triple over its alphabet and
            none distinguishes the two, because a word the mutant accepts and
            the reference does not still fails `strtod` on the leading

            and no such string exists over this parser's grammar. NOT
            declared: that is an argument this file cannot finish.


C. UNREACHED BY THE SEARCH BY CONSTRUCTION -- 1 (the negative control)
---------------------------------------------------------------------
  479d0b11  const_tweak   L49   MaxParamLength 200 -> 201

  The search passes its record length as a LITERAL 200 precisely so that this
  mutant is out of its reach, and it duly came back NONE. That is the
  instrument's negative control and it is the reason to trust the sixteen
  DIFFERS above.

  Its own answer is separate and is a corpus gap. The constant is used
  CONSISTENTLY -- the `Words` vector, `GetWords`'s element width, the READ's
  record length and `TRIM(Words(2))` all move together -- so the mutant is a
  renaming of the buffer width and differs from the reference only where a
  word is 200 or 201 characters long, because the reference's `GetWords`
  truncates at `LEN(Words) = 200`. R14 builds leads to EXACTLY the record
  width (`2:tail:*@200`), so the corpus has that shape; what it does not have
  is such a shape on a line `FindLine` matches.
