A. THE TWO DEFECTS, WHICH THE SURVIVORS WERE POINTING AT ALL ALONG
------------------------------------------------------------------
Both were found by PRICING a record against the reference before planting it --
the runbook's rule -- rather than by reading the translation. Both are recorded
with their wrong artifact before the fix (C12):
`evidence/ParseInput_Dbl_Opt/record_form_probe.FIRST.txt`.

1. `parse_real` copied the IEEE word into `char buf[64]` under `n < 62`.

       nan(<58 a's>)   63 characters
       gfortran        iostat=0     bits=7FF8000000000000    a NaN
       the C++         iostat=5010  bits=<the item untouched>

   Measured over every payload length a 200-byte record can carry
   (`nan_payload_probe.{f90,cpp}`): the two sides agree for word lengths up to
   62, DISAGREE for 63..200, and agree again at 201 where `Words(1)` truncates.
   138 lengths of 197.

   TWO OF THE THEN-SURVIVORS WERE MUTANTS OF THAT CONSTANT -- `97c42adb`
   (`n < 62` -> `n <= 62`) and `4c451ef0` (`n < 62` -> `n < 63`). Both make the
   translation LESS wrong. That is why no corpus killed them, and it is the
   sharpest thing in this dispatch: **a surviving mutant of a constant is worth
   asking whether the constant is right.**

2. `list_read_reals` had no repeat-count ceiling. `std::strtol` SATURATES at
   `LONG_MAX`, so an overflowing count came back positive and the item was
   stored.

       200000000*7   ref 0     got 0      the ceiling itself
       200000001*7   ref 5010  got 0      <- the divergence
       999...9*7     ref 5010  got 0      <- and its wide form

   The sibling `parseinary_opt.cpp` has the ceiling, measured for an INTEGER
   item. A repeat count is record GRAMMAR rather than item TYPE, so it carries
   -- and the three rows above are the check rather than the assumption.

Both repairs were priced BEFORE the sweep by diffing `(id -> site)` rather than
ids (RUNBOOK, unit #55). The first moved 25 ids onto different sites while the
id SET barely changed, and two declared equivalences were dropped because their
sites had ceased to exist. The second dropped one more to the 40-per-operator
cap. Nothing was carried across by name.


B. THE CORPUS GAP, WHICH WAS ONE GAP AND NOT TWENTY-ONE
--------------------------------------------------------
`_RECORD_TAILS` (loop `59aa876`) already built records that END at the buffer's
last byte, and this unit's corpus already had them: `2:tail:digits@200` was in
the harness artifact's `Reached` list at the previous dispatch. So the boundary
was reached and the guards still survived.

THE MISSING HALF IS WHAT THE MUTANT READS AT THAT BOUNDARY. The record is
`Words(1)`, one element of `CHARACTER(MaxParamLength) :: Words(2)` -- ONE
contiguous 400-byte object -- so byte 201 is `Words(2)(1:1)`, the first
character of the SECOND word of the matched line, which for this unit is the
search key. R14 has always planted that key as `'Aa'`. **`'A'` is not a digit,
not a `.`, not a sign and not an exponent letter**, so every value-scanner guard
took the same branch either way.

`_NEIGHBOUR_TAILS` (this dispatch) pairs each full-width lead with a neighbour
whose first character IS what the scan at that boundary tests. Eight forms, and
a ninth class that the first eight cannot reach:

    dig / frac       digits or a fraction to the last byte, a DIGIT after it
    expl / expq      digits to the last byte, an `e` / `q` after it
    sign / neg       digits to the last byte, a `+` / `-` after it
    point            digits to the last byte, a `.` after it
    fracE            a fraction to the last byte, an `e` after it
    repword          a legal count behind leading zeros, so the VALUE starts
                     near the record's end -- the only way `match_word`'s own
                     `p + LEN(word) > len` bound has two live sides
    fracsig/expsig   the same trick to make the last digits SIGNIFICANT. A
                     200-digit fraction cannot: digit 201 is a hundred and
                     eighty places past what a binary64 holds, so a mutant that
                     reads one more digit computes the SAME double. This is why
                     `frac` killed the integer scan's guard and left the
                     FRACTION scan's alive.
    pointend         a field that reaches the record's end having transferred
                     nothing but a sign
    over             a lead built to N + 1, the only shape in which the buffer
                     WIDTH constant `MaxParamLength` is observable at all

plus single-word values for a unit whose key is at word TWO -- `3*7`, `1*7`,
`0*7`, `1.5E+2`, `1.5E-2`, `1.5+2`, `1.5-2`, `.`, `..`, `.e`, the ceiling pair,
and `nan(...)`. The k = 3 families (`_TAIL_VALUES`, `_BLANK_TAILS`) put the key
at word 3 or later, and `FindLine` is called here WITHOUT `AryLen`, so it
matches on word 2 and nothing else: sixty `Reached` labels, of which the k = 3
ones never matched a line.

AND ONE THING THAT IS NOT A RECORD AT ALL. Three mutants differed from the
shipped translation ONLY in whether a transferred `0.0` was stored, and all 293
cases that reached the READ arrived with `Variable == 0.0` exactly -- because
`generate.py::_base` draws an unconstrained real at the midpoint of ±1e3, which
IS 0.0. `_PLANT_REAL_SENTINEL` gives the free `INTENT(INOUT)` scalar real a
second variant at -987.654 in the neighbour block. Measured, in
`harness_partition.txt`, on the two arms that reach the READ:

    Variable IN /= 0      before        after
    read-ok                    0          280
    error, msg refused         0          280

ALL 30 PLANTED RECORD FORMS WERE PRICED AGAINST THE REFERENCE FIRST, out of the
same two-element storage, and all 30 agree on (IOSTAT, bits):
`record_form_probe.txt`. That is the runbook's rule and it is what turned this
dispatch from a corpus change into two bug fixes.


C. THE FOUR EQUIVALENCE DECLARATIONS THIS DISPATCH WITHDREW, AND WHY
--------------------------------------------------------------------
The premise "`p == 0` whenever `parse_real` is entered" was stated in
`mutation/ParseInput_Dbl_Opt.equivalences.md` and carried five declarations.
**It is false.** `list_read_reals` reaches `parse_real` from two places, and the
second is the repeat-count fall-through, where `p == q + 1`. The corpus that
had no `*` in any matched line could not contradict it; the corpus that has one
killed two of the five outright (`ec2c7596`, `2a6d08a0`) and `vit_mutate.py`
named them in `declared_but_killed`.

Two more resting on the same premise were withdrawn in the same edit. One
(`52112be9`) the corpus then KILLED, which is the confirmation that withdrawing
it was right. The other (`575c6151`) is re-declared on an argument that does not
use the premise at all.

**A fact about where a corpus enters a function is not a fact about the
function**, and an equivalence written on one is a corpus gap wearing a
declaration's name.
