ParseInput_Int_Opt -- the two gate red tests, PREDICTED BEFORE THEY RUN
================================================================================

The RUNBOOK records that this family's gate answer is set by the FAILURE CLASS
and not by the site: three units, four runs, two numbers.

    every parsed value is one greater
      gate/ParseInAry_Opt.redtest.parsed-value.json      1,857,893 / 5,252,000  147 ch
      gate/ParseInput_Dbl_Opt.redtest.parsed-value.json  1,857,893 / 5,252,000  147 ch

    the parse FAILS, so ErrVar%aviFAIL = -1
      gate/ParseDbAry_Opt.redtest.survivor-2a9e1695.json 1,583,216 / 4,732,000  131 ch
      gate/ParseInput_Dbl_Opt.survivor.9e00d730.json     1,583,216 / 4,732,000  131 ch

So a red test on this unit can be predicted TO THE VALUE, and a red test whose
count can be predicted exactly is one that can be WRONG -- which is what makes
it evidence about the instrument rather than a formality.


1. parsed-value -- every value this unit reads out of the input file is one
   greater than the file says.

       rosco/controller/src/parseinput_int_opt.cpp
       from:  *Variable = static_cast<int>(value);
       to:    *Variable = static_cast<int>(value) + 1;

   PREDICTED EXACTLY 1,857,893 of 5,252,000 across 147 of 351 channels,
   scenarios all 27 alive.

   The prediction rests on the failure class being identical to the two runs
   above -- every parsed control parameter is wrong by a fixed amount from
   timestep zero -- and NOT on the item type. If this unit's integers moved a
   DIFFERENT number of values from the sibling's reals, that is the finding: it
   would say the count is set by which parameters a unit reads rather than by
   when each scenario first diverges, and the family rule in the RUNBOOK would
   need the item type added to it.

   A count of ZERO would mean the gate cannot see this unit at all. The unit is
   called 1,680 times across the 27 scenarios (coverage/line_coverage.json,
   ROSCO_Helpers.f90:115), so a zero would be a finding about the gate.


2. default-arm -- the value substituted when the input file does not supply the
   parameter.

       from:  *Variable = 0;
       to:    *Variable = 12345;

   PREDICTED EXACTLY 0 of 5,252,000.

   Predicted from coverage rather than hoped for: `ROSCO_Helpers.f90:154`
   (`IF (.NOT. FoundLine)`) has 1,680 hits and `:155`-`:162`, the whole
   not-found arm, has NO COUNTER AT ALL. Every `Examples/DISCON*.IN` supplies
   every INTEGER parameter this unit asks for, so `FoundLine` is TRUE at all
   1,680 calls and the gate cannot reach the arm. The differential harness
   reaches it on 9,011 of 12,059 cases, which is the layer that covers it.

   The zero is only worth something NEXT TO the non-zero on the same build, so
   the two are run as a PAIR.


   MEASURED
   --------
   (filled in after the runs)
   MEASURED, 2026-08-19, both on the same build, run as a pair
   -----------------------------------------------------------

       parsed-value   PREDICTED 1,857,893 of 5,252,000, 147 of 351 channels,
                                all 27 scenarios alive
                      MEASURED    370,646 of   728,000,  22 channels,
                                mismatches in scenarios 19, 20 and 27 only
                      revert-verified 0 of 5,252,000

       default-arm    PREDICTED 0 of 5,252,000        MEASURED 0   EXACT
                      revert-verified 0 of 5,252,000

   THE FIRST PREDICTION IS FALSIFIED, AND THAT IS WORTH MORE THAN A HIT.

   An INTEGER control parameter is a MODE, not a gain. Adding one to every value
   this unit parses does not perturb a trajectory -- it selects a different
   controller path in every scenario, and 23 of the 27 then produce no
   comparable output at all. The gate compared 728,000 values against the green
   run's 5,252,000.

   So the family rule -- "the gate's answer is set by the FAILURE CLASS, not by
   the site" -- survives, and this is a THIRD class beside the two the RUNBOOK
   records:

       every parsed value is wrong        1,857,893 / 5,252,000   147 ch  (REAL)
       the parse FAILS, aviFAIL = -1      1,583,216 / 4,732,000   131 ch
       every parsed MODE is wrong           370,646 /   728,000    22 ch  (INTEGER)

   The distinction the first two could not make is between "the failure class"
   and "the item type", because both of those runs perturbed a REAL. This one
   perturbs an INTEGER at the same kind of site and lands somewhere else, which
   settles it: the class is about what goes wrong DOWNSTREAM, and for this unit
   what goes wrong downstream is a mode.

   Writing the prediction down is what made this visible. A red test that cannot
   be wrong is not evidence about the instrument; this one could be wrong, was,
   and the being-wrong is the measurement.

   THE SECOND IS EXACT, and it is a zero that was predicted rather than hoped
   for. Both artifacts carry their prediction in a `--note`, so a reader who
   opens the zero finds the expectation beside the number.
