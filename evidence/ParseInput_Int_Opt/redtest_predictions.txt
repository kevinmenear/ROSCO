================================================================================

A red test whose number can be predicted exactly is one that can be WRONG, and a
red test that cannot be wrong is not evidence about the instrument (RUNBOOK, the
Parse* family's gate rule, run here on the differential harness instead).

Every number below is read off `harness_partition.txt`, which classifies all
11,863 cases by the arm the REFERENCE took -- read off the reference's own
returned message and its own returned `aviFAIL`, not off the translation.

THE CELL THE PROBE COULD NOT SPLIT, and the identity that resolves it for free.
R13's short-capacity block sizes `ErrVar%ErrMsg`'s staging buffer below the
message on 761 cases, so the message the reference returns is the one the case
ARRIVED with. Both the `.NOT. AllowDefault_` arm and the READ-error arm land
there -- both set `aviFAIL = -1`, neither writes a record -- and nothing in the
returned state separates them. Write

    A = the `.NOT. AllowDefault_` cases inside that cell
    B = the READ-error cases inside that cell
    A + B = 761                                     <- fixed by the table

Two point predictions would each be a guess about the split. Two BRACKETS are
not: the interval is derivable, and the SUM is a number the table fixes before
either run (unit #56's rule, and unit #47's arm-attribution control run the
other way round).

   THE INTEGER READER MAKES ONE HALF OF THIS EXACT WHERE THE REAL ONE DOES NOT.

   CONTROL, stated before either run and checkable afterwards:

       (measured #3 - 1,807) + (measured #4 - 169) = 761

   If the two excesses do not sum to 761 the arm attribution is wrong, and that
   is a finding about the partition rather than about either stub.


AND ONE NUMBER THAT IS NOT A PREDICTION. `Variable IN /= 0` is 360 of 11,863,
and 0 of the 184 read-ok cases and 0 of the 761 refused-message cases. So every
case that reaches the READ and succeeds arrives with `Variable == 0`. A mutant
whose only effect is to store 0 where the reference stores nothing is invisible
on those cases -- the same shape unit #56 measured for its REAL item and
refused to buy with a range pin, because a pin is global to the unit and would
delete R6's integer ladder from this unit's only free scalar. Measured here
rather than inherited; the mutation survivors are read against it.

THE ADDITIVE CONTROL FAILED, AND IT IS REPORTED RATHER THAN CLAIMED.

    old case file  6,022,734 bytes
    new case file  6,044,700 bytes
    old is a PREFIX of new:  False

Unit #56's rule is to take `b[:len(a)] == a` on every corpus-extending change,
and it is taken here. It does NOT hold, and the reason is structural rather than
a slip: the entries were added to `_NEIGHBOUR_VALUES`, which is consumed inside
the `n:` block that R14 appends after EVERY plant index, so new cases from the
k = 1 block displace everything the k = 2 and k = 3 blocks emit after it. There
is no ordering of that tuple that makes the change a suffix append.

So this is a DIFFERENT corpus, not an extended one, and every layer that reads
the corpus was re-taken on it -- harness, partition, all four stubs, line
coverage, both mutation sweeps. Nothing carries over from the 11,863-case run
except the mutant IDs, which are a function of the translation and not of the
corpus.
