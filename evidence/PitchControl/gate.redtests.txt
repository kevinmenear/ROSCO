RT3 -- THE PREDICTION WAS WRONG ABOUT THE PROGRAM, NOT ABOUT THE INSTRUMENT
---------------------------------------------------------------------------
The prediction said a non-zero here "would mean the coverage data is wrong
about this line, which is a finding about the instrument". IT WOULD NOT, and
recording that is the point of this entry.

Inverting `IPC_SatMode == 1` to `!= 1` does not leave a dead block dead. It
makes the block run on every call in which IPC_SatMode is not 1 -- which is
every call in all 27 scenarios. So 177,425 moved values say the block is now
LIVE, and say nothing whatever about whether it was reachable before.

The prediction's own words were "on the corpus the gate drives this block is
dead in BOTH directions", and that clause is simply false. A guard inversion is
not a negative control for a dead arm; it is the strongest possible POSITIVE
perturbation of one.

RT5 -- THE CONTROL THAT ACTUALLY CONTROLS: PERTURB TOWARD ABSENCE
------------------------------------------------------------------
    if (false && CntrPar->IPC_SatMode == 1) {

    0 of 5,252,000 moved, 0 scenarios broken, revert 0

This is RUNBOOK's `if (false && ...)` instrument, recorded there for Conv2UC as
a way to perturb toward ABSENCE rather than toward a different answer. It is
the right shape for a dead arm because it is a no-op exactly when the arm never
runs, and it removes an effect otherwise. Zero, with all 27 scenarios alive and
5,252,000 values compared, says the IPC saturation block executes in no
scenario -- which is what RT3 was supposed to establish and could not.

RT4 -- A NEGATIVE CONTROL THAT WOULD HAVE BEEN "CONFIRMED" BY A NUMBER THAT
MEASURED NOTHING, AND THE GATE IS WHAT CAUGHT IT
----------------------------------------------------------------------------
Predicted EXACTLY 0. Measured 0. AND THE PREDICTION IS STILL REFUTED, because
the zero is over 468,000 values and not 5,252,000:

    NOT 'the gate cannot see it': the perturbation STOPPED 23 of 27
    scenario(s) from running at all, and those scenarios ran on the revert.

Forcing `OL_Mode > -1000000` turns the open-loop override on in every scenario,
and the three interp1d calls then read open-loop tables no scenario allocated.
The scenarios die. A dead scenario produces no values, `mismatched` counts
VALUES, and 0 of 468,000 renders identically to 0 of 5,252,000 in any reader
that looks only at `mismatched`.

The prediction contains the contradiction in plain sight -- it says the
perturbation "FORCES the open-loop override ON in every scenario" and then that
"if OL_Mode really is <= 0 in all 27 scenarios the count is 0". Both cannot
hold: forcing an override on is what makes the count large. It was written as
the STRONGER of the two controls and it is the weaker.

`scripts/gate.py`'s `perturbation_broke_scenarios` is the only thing between
that and a recorded green. It is worth more than the red test it invalidated.
