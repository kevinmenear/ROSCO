THE CAUSE IS ONE LINE OF THE REFERENCE, AND IT IS A REAL READ
--------------------------------------------------------------------------------
`harness/statevary.py::read_set` marks an argument read WHOLE when the body
mentions it as a bare word -- "it was handed to a callee, and what the callee
touches is not visible here". This unit does that with `LocalVar`:

    Controllers.f90:346
      LocalVar%GenTqAz = PIDController(LocalVar%AzError, CntrPar%RP_Gains(1),
          ..., LocalVar%piP, LocalVar%restart, objInst, LocalVar)

`objInst` and `LocalVar` are both passed whole, and `ErrVar` is passed whole to
`interp1d` and to `unwrap`. That is not an over-reading of the source: those are
the arguments the reference hands over. `LocalVar` alone expands to 179 C
parameters, which is where 224 - 55 comes from.

PROBE 2 -- HOW MANY BYTES PER CASE (`probe_corpus_size.py`, 16 seconds)
--------------------------------------------------------------------------------
Run under `ulimit -v 5500000` so the failure is a `MemoryError` with a traceback
rather than a SIGKILL with nothing:

    cases     2000  maxrss      398 MB
    cases     4000  maxrss      775 MB
    cases     6000  maxrss     1151 MB
    ...
    cases    28000  maxrss     5294 MB
    MemoryError after 28296 _case_impl calls

    File "harness/generate.py", line 2150, in generate
      cases.append(_case(sig, ex0, rng, {p.name: v, **fv}, held=held))

The slope is FLAT over fourteen points: (5294 - 398) MB / 26,000 cases =
**188 KB per case**, and the intercept is 21 MB. It is not a leak and it is not
a spike; it is what one case of this signature costs.

Where the 188 KB is: `_case_impl` fills every array-valued parameter per case
(`harness/generate.py:1885`, `_fill_array`). `avrSWAP` is 3,000 doubles, and a
Python list of 3,000 distinct floats is 3000 x (8 byte pointer + 32 byte float
object) = 120 KB -- 64% of the total. The other ~68 KB is the remaining 480
parameters, most of them arrays at extent 3 to 12.

THE ARITHMETIC, AND WHY MORE MEMORY IS NOT THE ANSWER
--------------------------------------------------------------------------------
    generation      143,261 cases x 188 KB  =  27.0 GB      VM has 7.736 GiB
    fits in the VM   7.7 GB / 188 KB        =  ~41,000 cases  (29% of the corpus)

Even granting unlimited memory for the generation, the two layers downstream do
not fit the campaign's own shape:

    emit            IPC's 83,754 cases wrote an 860 MB case file with no
                    avrSWAP. This signature carries ~4,500 doubles per case, so
                    143,261 cases is ~5.2 GB on disk -- and `harness/emit.py`
                    has a MEASURED SIGKILL ceiling between 84,754 and 95,310
                    cases in this same VM (STATUS.md, unit #53).
    mutation        `vit_mutate.py` rebuilds and re-runs the WHOLE corpus per
                    mutant. RefSpeedExclusion: 36 mutants over 13,777 cases.
                    143,261 cases is 10x that corpus at 3x the per-case width.

So the wall is not "the VM is small". It is that this unit's signature makes the
campaign's generated corpus an order of magnitude larger than any it has run,
and the differential-harness and mutation layers are both priced per case.

WHAT WOULD MOVE IT, PRICED, AND NOT DONE HERE
--------------------------------------------------------------------------------
1. STATED RANGES. `statevary.constrain` sets `bounds_source = stated:<name>` for
   any parameter named in `harness/ranges.toml`, and `Signature.defaulted` is
   what R6's three big sub-counts iterate over. Naming the 160 unconstrained
   parameters would cut the count in roughly that proportion. REFUSED HERE, and
   the reason is the file's own rule: every entry NARROWS the domain and must
   carry the measurement or the source line that forces it. 160 entries written
   in one dispatch to make a number smaller would be 160 judgements nobody made.
   What is worth writing is the handful this unit's own arithmetic needs -- and
   that is a corpus DESIGN, which wants its own dispatch.

2. A REPRESENTATION FIX IN `_case_impl`. Storing a real array fill as
   `array.array('d')` instead of a list of float objects is the same doubles at
   8 bytes each: 188 KB -> ~68 KB, a 2.8x cut, with a decisive positive control
   available (regenerate FlapControl's corpus and require the `.bin` to be
   BYTE-IDENTICAL). It does not close the gap alone -- 143,261 x 68 KB is still
   9.7 GB -- and it touches the generator that produced every other unit's
   evidence, so it is a change that wants its own measurement, not a change made
   in passing while a unit is open (X2 says fix the tool you control; it does
   not say fix it inside another unit's dispatch).

3. A NARROWER READ SET. `PIDController` is unit #34 and its translation states
   exactly which `LocalVar` fields it touches, so the whole-argument
   over-approximation could in principle be replaced by a transitive read set.
   That is a change to how EVERY unit's corpus is chosen (X3), and it would make
   this unit's evidence incomparable with the 59 before it.

WHAT THIS UNIT HAS INSTEAD, AND WHAT IT DOES NOT COVER
--------------------------------------------------------------------------------
See `evidence/VariableSpeedControl/README.md`. The gate is the layer that does
not read a case file, and it is the one this dispatch took. The differential
harness, the post-integration harness and the mutation score are NOT taken, and
the unit is `deferred` for exactly that reason rather than closed.
